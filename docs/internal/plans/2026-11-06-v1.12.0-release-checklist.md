#### Assessment of #693 (verified 2026-11-25)

The `golang:1.26-bookworm` tag resolved to image digest
`sha256:ea47ee45f1284d60f9cc09cb2c3bb4f508c256b640bd8bb30342ff13d1adcb52` (pushed
2026-11-24), whose config declares **`GOLANG_VERSION=1.26.11`** — i.e. **at or above the
fix floor**. The same digest was used by the Container security release gate run against the
v1.12.0 candidate, and that gate **passed**.

So the artefact built by the current Dockerfile is **not** affected. The residual risk is
**reproducibility, not exploitability**:

- The `go.mod` floor (`1.26.9`) is **below** the fix line, so a build with an exactly-1.26.9
  toolchain **would** be vulnerable. Nothing in the build pins the toolchain to a fixed
  version.
- The Dockerfile uses a **floating** tag. A future rebuild — including the release
  publication build — resolves whatever `1.26-bookworm` points to *at that moment*. If the
  tag were rolled back or a mirror served an older base, the published image would silently
  regress below the fix floor.
- The Trivy gate does **not** currently flag it (Trivy scans the runtime image; the Go
  stdlib version baked into the binary is not surfaced as a finding for this case).

**Therefore:** fixing the `go.mod` floor to `1.26.11` and **pinning the builder image
digest** closes the residual. Note that `0c6ab72a` (the Go dependency group bump already on
`main`) did **not** change the `go` directive — it only bumped module versions — so this
finding is **still open** in `main` and in the v1.12.0 candidate.

**Not material to v1.12.0 scope:** [#706](https://github.com/uniskela/ts6-manager/issues/706)
(YouTube `!stream` 403), [#692](https://github.com/uniskela/ts6-manager/issues/692)
(music-bot route validation), [#694](https://github.com/uniskela/ts6-manager/issues/694)
(React Query cache on user change), [#691](https://github.com/uniskela/ts6-manager/issues/691)

### Session-hardening invariants (hard gate — unchanged by this proposal)

P1-A (admin credential/disable refresh revoke) and P1-B (atomic refresh rotation / reuse detection, including login mint safety) are part of this gate. v1.12.0 must not ship until these invariants are proven on real SQLite and independently reviewed:

1. After an administrator password reset or account disable for a user, no new refresh token may be minted for that user (**covers both token rotation and login**).
2. A refresh token may be consumed at most once; replay of a consumed token revokes only that session family.
3. Unrelated users/devices keep valid sessions; **do not globally revoke all devices as the default fix**.
4. Access-JWT lifetime and established WebSocket teardown are out of scope unless separately implemented and tested — do not claim them from P1-A/P1-B alone.

**P1-A alone is not releasable for this gate.** Code merges of P1-A/P1-B onto `main` do **not** replace the independent review requirement.
