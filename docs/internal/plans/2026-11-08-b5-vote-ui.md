# B5 — propose button, vote banner and result (listener remote UI)

Status: draft branch `feat/listener-b5-vote-ui`, based on `main` @ `192ae0b`. Frontend only. Not for merge before its integration review and owner GO (#442, #465).

## What it adds

- **Propose control** in a playlist's detail view (Playlists tab):
  - voting on: "Propose this playlist", with the window, threshold and the alone-means-queued rule spelled out;
  - voting off: "Add all N songs".
  - Explains each reason it cannot be used before anyone presses it: browse-only playlist, no permission, empty, over the size limit (`maxTracks` from `/state`), or a vote already running.
- **Vote banner** across the top of the remote for the open vote on this bot and channel, or the last one for 30 s after it closes, as `/state` reports it:
  - playlist name and song count;
  - tally ("2 yes · 1 no · needs 4 of 5 listeners") and a decorative bar;
  - countdown (`role="timer"`).
- **Ballots and cancel:**
  - Yes and No are toggle buttons (`aria-pressed`). A listener who voted can withdraw.
  - The requester sees only "Cancel vote": their yes is automatic, and the contract refuses a requester withdrawal.
  - Listeners without the vote permission get a plain sentence instead of buttons.
- **Results:** one plain sentence for each end reason in the contract.
- **Accessibility:**
  - A polite live region announces a new vote, the listener's own ballot, the last ten seconds and the result.
  - Proposing moves focus to the banner. Errors are `role="alert"` and focused.
  - Every control is at least 44 px tall, and the page has no horizontal overflow at 375 px or 1280 px.
- **Client additions:**
  - `/state` parsing for `permissions.requestPlaylist`, `permissions.vote`, `playlistRequests` and `vote`. An unreadable vote hides the banner rather than failing the remote.
  - The four B3 endpoints. Vote ids are checked against the 22-character format before any request is built.
  - `RemoteHttpError.retryAfterSeconds` from 429 `Retry-After`.

No backend change. No change to the vote rules, rate limits, sessions, CSP or remote bundle isolation. Nothing is stored in the browser.

## Server stays authoritative

- Permissions, vote status, tallies, deadline and result always come from `/state` or the mutation's answer. The UI never computes a pass, fail or tally.
- The countdown is display-only. At zero it shows "Closing…" and reads `/state` once. Ballots stay enabled and the server answers (404 "This vote has already ended." once settled).
- A `/state` poll that started before a ballot, cancel or proposal answer keeps the newer vote, so a slow poll cannot undo the listener's own ballot on screen. The next poll is authoritative.
- Direct queueing (voting off) and proposals are refused by the backend on permission, visibility, size and emptiness. The UI explanations are hints only.

## Duplicate protection

- Each control is locked while its request runs, and every remote mutation is serialized (`enqueueRemoteMutation`). Nothing is retried automatically.
- After a direct queue, the button stays "Added to the queue" until the listener leaves the playlist, so a stray tap cannot queue it twice.
- A 503 or a lost connection on a proposal says "The request could not be confirmed. Check Up next before trying again.", because the request may have arrived.

## Known limits

- The countdown uses the phone's clock, clamped to the vote window (`windowSeconds`, 60 by default). At zero it shows "Closing…" and asks `/state` once; the server decides the result.
- Other listeners' ballots appear within one five-second poll. There is no push channel.
