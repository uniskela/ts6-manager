## 1. Safe staging setup (#632 candidate)

### Why this approach

**Do not** use `docker-compose.pr-test.yml` for operator acceptance. That file publishes TeamSpeak voice, Query, file transfer, metrics, and the frontend on all host interfaces (`0.0.0.0`). Compose also **concatenates** `ports` across layered files, so an “override” cannot safely close those publishes.

Use the standalone [`docker-compose.accept-staging.yml`](../../../docker-compose.accept-staging.yml) instead:

- Fixed project name `ts6-accept-632` (volumes/network cannot collide with pr-test, beta, or production).
- Frontend only on `127.0.0.1` (private HTTPS / Tailscale Serve).
- TeamSpeak voice only on an explicit private bind IP + non-default host port.
- ServerQuery (10022), file transfer (30033), and metrics (9187) are **not** published; Query stays on the compose network for bootstrap/health.
- Generated test-only secrets; no production TS DB, Portainer, or production compose.

Prefer an isolated staging VM/LXC/Docker host. Docker rootless alone is **not** network isolation.

### Required host port bindings (effective)

| Service | Host binding | Purpose |
|---------|--------------|---------|
| `frontend` | `127.0.0.1:${ACCEPT_HTTP_PORT:-13100}` → `80/tcp` | Admin UI, `/remote`, `/api` via Serve/proxy |
| `teamspeak` | `${TS_VOICE_BIND_IP}:${TS_VOICE_HOST_PORT:-19987}` → `9987/udp` | Voice for lab clients only |
| `sidecar` | `127.0.0.1:${WEBRTC_UDP_PORT:-10000}` → WebRTC UDP | Optional preview (loopback) |
| `backend` | *(none)* | API only through frontend proxy |
| ServerQuery / metrics / file transfer | *(not published)* | In-container / compose network only |

Defaults avoid collisions with a host TS on `9987`, pr-test frontend `:3000`, and beta `:13000`.

### Prerequisites

- Disposable Docker host (prefer dedicated VM/LXC). Never production Portainer edits.
- ≥3 TeamSpeak client identities for F6; ≥2 for F2–F5/F7.
- Private HTTPS origin for `PUBLIC_URL` (production-mode backend rejects plain `http://` for `!remote`). Tailscale Serve to loopback `ACCEPT_HTTP_PORT` is the usual path.
- One private IPv4 for `TS_VOICE_BIND_IP` (Tailscale or lab LAN). Never `0.0.0.0`, never a production TS address.

### Private HTTPS access

1. Keep frontend on `127.0.0.1:13100` (or your `ACCEPT_HTTP_PORT`).
2. Point Tailscale Serve (or another private reverse proxy) at that loopback port with TLS.
3. Set `PUBLIC_URL` to that HTTPS origin (no trailing path). Rebuild/recreate backend if you change it after first boot.
4. From intended test browsers: open `PUBLIC_URL` → `/setup` then `/login`; after `!remote`, the one-time link must share that same HTTPS origin for `/remote` and `/api`.

### Access

| Surface | URL / how |
|---------|-----------|
| Admin UI + API proxy | `https://<PUBLIC_URL host>/` (Serve → `127.0.0.1:13100`). Local-only: `http://127.0.0.1:13100` for admin prep. |
| Listener remote | `!remote` → one-time **HTTPS** link on `PUBLIC_URL`. Same origin serves `/remote` + `/api`. |
| TeamSpeak voice | Client → `${TS_VOICE_BIND_IP}:${TS_VOICE_HOST_PORT}` (UDP). Lab server only. |
| Backend / ServerQuery / metrics | Not on the host. Do not publish them for this test. |

## 3. Search — C5 / C6

### C5 — Search, queue, spent result, duration/live

| | |
|--|--|
| **Listeners** | 1 full-permission (add/queue) in bot channel |
| **Initial state** | Bot connected; queue empty or known; Search visible |
| **Actions** | 1) `!remote` → open link. 2) Search a short supported track; **+** add. 3) Attempt **+** again on the same result row / refresh and reuse spent id if still shown. 4) Search/paste a live or over-duration item per server rules. |
| **Expected UI** | Track appears in Up next / Requests; spent/expired add fails with clear message and row drops; live/too-long refused, not queued. |
| **Expected queue/history** | Exactly one queue of the good track; no queue for refused/spent. |
| **Evidence** | Cropped remote screenshots; Requests list; backend log line class (no secrets). |
| **PASS** | All four behaviours hold on this stack. **FAIL** if duplicate queue from spent id or live slips through. |

### C6 — Browse-only cannot search; backend 403

| | |
|--|--|
| **Listeners** | 1 browse-only (no add/queue group) in bot channel |
| **Initial state** | Same bot/channel; voting irrelevant |
| **Actions** | 1) `!remote` as browse-only. 2) Confirm **Search is hidden** (browse-only UI gate). 3) From the same authenticated remote browser session (DevTools → Network), force `POST /api/listener-remote/search` with a minimal JSON body such as `{"query":"test"}` using the session’s existing `Authorization: Bearer …` header **or** replay the request from an earlier full-permission capture after switching to the browse-only session cookie/token already in that tab. Do **not** copy the token into notes, tickets, or chat. Expect HTTP **403** with `code: "permission_denied"` and no provider/search side effect. Library/playlists browse may still work. |
| **Expected** | No Search UI; forced search 403; no queue. |
| **Evidence** | Screenshot without Search; Network panel status **403** + `permission_denied` only (redact Authorization). |
| **PASS** | UI gate + live 403 on this stack. **FAIL** if Search offered or search succeeds. Unit/Playwright coverage of search deny is **not** live PASS. |

## 4. Playlist voting — F2–F7 (#632)

**Shared settings unless noted:** voting **on**, threshold **100%**, window known; playlist `request`able; bot idle or playing (record which).  
**Automated races** (Playwright) ≠ live PASS. F2–F7 live tests remain **mandatory** for #632 acceptance.

### F2 — Remote Yes (≥2 listeners)

1. **Listeners:** A (requester) + B (peer), both full remote.  
2. **State:** No open vote; queue baseline noted.  
3. **Actions:** A remote → Playlists → propose/request playlist. B remote → **Yes**.  
4. **Expected UI:** Banner shows open vote then pass; Search still present when permitted.  
5. **Queue/history:** Playlist tracks queued **once**; Requests history once for those tracks.  
6. **Evidence:** Both remotes; Up next / Requests.  
7. **PASS:** Single queue after B yes. **FAIL:** No queue, double queue, or banner missing on B.

### F3 — Chat Yes (≥2)

1. Same as F2 setup with fresh vote.  
2. **Actions:** A proposes (remote). B: `!playlistvote yes` in channel.  
3. **Expected:** Private reply success; pass + single queue/history.  
4. **PASS:** Same as F2 via chat. **FAIL:** Chat ignored or double queue.

### F4 — Requester No cancel (≥2)

1. A proposes; vote open.  
2. **Actions:** A: `!playlistvote no` (or remote cancel if shown for requester).  
3. **Expected:** Vote cancelled; **nothing** queued; no playlist history rows for this attempt.  
4. **PASS:** Cancel clean. **FAIL:** Tracks still enqueue.

### F5 — Post-approval duplicate prevention (≥2)

1. Complete a pass (remote or chat).  
2. **Actions:** B sends another `!playlistvote yes` / remote Yes on ended vote.  
3. **Expected:** Refusal / “no open vote”; queue count unchanged.  
4. **PASS:** No second enqueue. **FAIL:** Duplicate tracks.

### F6 — Concurrent remote + chat (≥3 listeners)

1. **Listeners:** A requester + B + C; threshold 100%.  
2. **State:** A proposes; need **two** yeses from non-requester electorate (or adjust so one yes alone does not finish—if sole-electorate auto-pass interferes, add listeners first). Prefer: three humans in channel so two peer yeses are required at 100%.  
3. **Actions:** On an open vote that still needs more yeses, B taps remote **Yes** and C sends `!playlistvote yes` as close together as practical (or both peers yes nearly together when two are required).  
4. **Expected:** Exactly **one** pass; **one** queue; **one** history set.  
5. **Evidence:** Timestamps optional; Up next count; Requests.  
6. **PASS:** Single enqueue under concurrency. **FAIL:** Double queue/history.  
7. **Note:** Unit/Playwright races are separate; this row needs the lab server.

### F7 — Private data protection (≥2)

1. During F2–F6, inspect remote JSON (browser Network `/state`, vote payloads) and chat private replies.  
2. **Expected:** Counts / ownBallot / isRequester only; **no** UIDs, voter lists, or filesystem paths.  
3. **PASS:** No leaks. **FAIL:** Any UID/path in UI or reply text.
