## 1. Safe staging setup (#632 candidate)

### Why this approach

Build `docker-compose.pr-test.yml` from the **exact** #632 tip. That checkout already contains merged Search (#617/#631) plus vote UI, against the same backend vote/search APIs as `main` (plus vote UI only). Named volumes keep data off production. Host binds stay loopback-oriented as in the compose file.

### Prerequisites

- Docker **rootless** (or equivalent non-production host). Never `/var/run/docker.sock` rootful changes for this test.
- pnpm 9 / git optional for SHA check only.
- ≥3 TeamSpeak client identities (human listeners) for F6; ≥2 for F2–F5/F7.
- HTTPS origin for `!remote` (production-mode backend rejects plain HTTP). Prefer Tailscale Serve / Funnel to the local frontend, or another private TLS front.

### Exact commands

```bash
# Disposable directory — not the production checkout
mkdir -p ~/ts6-accept-632 && cd ~/ts6-accept-632
git clone https://github.com/uniskela/ts6-manager.git .
git fetch origin
git checkout --detach 115a7eaef31c5ba965b64ca9c6c42fff30d1548d
git rev-parse HEAD   # must print 115a7eaef31c5ba965b64ca9c6c42fff30d1548d

cp .env.pr-test.example .env
# Edit .env:
#   PUBLIC_URL=https://<your-private-https-origin>   # required for !remote
#   Keep JWT_SECRET / ENCRYPTION_KEY / SIDECAR_SECRET as local-only test values
#   Do not copy production secrets into this file

export GIT_SHA=115a7eae
docker compose -f docker-compose.pr-test.yml down -v   # wipe prior pr-test volumes if any
```

Wait until `teamspeak` is healthy and backend has started (compose already waits on Query ports).

## 3. Search — C5 / C6

### C5 — Search, queue, spent result, duration/live

| | |
|--|--|
| **Listeners** | 1 full-permission (add/queue) in bot channel |
| **Initial state** | Bot connected; queue empty or known; Search visible |
| **Actions** | 1) `!remote` → open link. 2) Search a short supported track; **+** add. 3) Attempt **+** again on the same result row / refresh and reuse spent id if still shown. 4) Search/paste a live or over-duration item per server rules. |
| **Expected UI** | Track appears in Up next / Requests; spent/expired add fails with clear message and row drops; live/too-long refused, not queued. |
| **Expected queue/history** | Exactly one queue of the good track; no queue for refused/spent. |
| **Evidence** | Cropped remote screenshots; Requests list; backend log line class (no secrets). |
| **PASS** | All four behaviours hold on this stack. **FAIL** if duplicate queue from spent id or live slips through. |

### C6 — Browse-only cannot search; backend 403

| | |
|--|--|
| **Listeners** | 1 browse-only (no add/queue group) in bot channel |
| **Initial state** | Same bot/channel; voting irrelevant |
| **Actions** | 1) `!remote` as browse-only. 2) Confirm Search **hidden**. 3) Optional: from a tool, `POST /api/listener-remote/search` with that session → expect **403** `permission_denied` (no provider call). Library/playlists browse may still work. |
| **Expected** | No Search UI; forced search 403; no queue. |
| **Evidence** | Screenshot without Search; optional 403 status only (no session body in notes). |
| **PASS** | UI gate + 403. **FAIL** if Search offered or search succeeds. |

## 4. Playlist voting — F2–F7 (#632)

**Shared settings unless noted:** voting **on**, threshold **100%**, window known; playlist `request`able; bot idle or playing (record which).  
**Automated races** (Playwright) ≠ live PASS.

### F2 — Remote Yes (≥2 listeners)

1. **Listeners:** A (requester) + B (peer), both full remote.  
2. **State:** No open vote; queue baseline noted.  
3. **Actions:** A remote → Playlists → propose/request playlist. B remote → **Yes**.  
4. **Expected UI:** Banner shows open vote then pass; Search still present when permitted.  
5. **Queue/history:** Playlist tracks queued **once**; Requests history once for those tracks.  
6. **Evidence:** Both remotes; Up next / Requests.  
7. **PASS:** Single queue after B yes. **FAIL:** No queue, double queue, or banner missing on B.

### F3 — Chat Yes (≥2)

1. Same as F2 setup with fresh vote.  
2. **Actions:** A proposes (remote). B: `!playlistvote yes` in channel.  
3. **Expected:** Private reply success; pass + single queue/history.  
4. **PASS:** Same as F2 via chat. **FAIL:** Chat ignored or double queue.

### F4 — Requester No cancel (≥2)

1. A proposes; vote open.  
2. **Actions:** A: `!playlistvote no` (or remote cancel if shown for requester).  
3. **Expected:** Vote cancelled; **nothing** queued; no playlist history rows for this attempt.  
4. **PASS:** Cancel clean. **FAIL:** Tracks still enqueue.

### F5 — Post-approval duplicate prevention (≥2)

1. Complete a pass (remote or chat).  
2. **Actions:** B sends another `!playlistvote yes` / remote Yes on ended vote.  
3. **Expected:** Refusal / “no open vote”; queue count unchanged.  
4. **PASS:** No second enqueue. **FAIL:** Duplicate tracks.

### F6 — Concurrent remote + chat (≥3 listeners)

1. **Listeners:** A requester + B + C; threshold 100%.  
2. **State:** A proposes; need **two** yeses from non-requester electorate (or adjust so one yes alone does not finish—if sole-electorate auto-pass interferes, add listeners first). Prefer: three humans in channel so two peer yeses are required at 100%.  
3. **Actions:** On an open vote that still needs more yeses, B taps remote **Yes** and C sends `!playlistvote yes` as close together as practical (or both peers yes nearly together when two are required).  
4. **Expected:** Exactly **one** pass; **one** queue; **one** history set.  
5. **Evidence:** Timestamps optional; Up next count; Requests.  
6. **PASS:** Single enqueue under concurrency. **FAIL:** Double queue/history.  
7. **Note:** Unit/Playwright races are separate; this row needs the lab server.

### F7 — Private data protection (≥2)

1. During F2–F6, inspect remote JSON (browser Network `/state`, vote payloads) and chat private replies.  
2. **Expected:** Counts / ownBallot / isRequester only; **no** UIDs, voter lists, or filesystem paths.  
3. **PASS:** No leaks. **FAIL:** Any UID/path in UI or reply text.
